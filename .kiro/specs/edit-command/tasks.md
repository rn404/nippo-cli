# Implementation Plan

- [x] 1. ドメイン・ユーティリティ層の実装
- [x] 1.1 (P) 当日ログのcontent編集ロジックとユニットテスト
  - `internal/log` に、hashで当日ログのアイテムを読み取り専用に検索する関数を追加する
  - `internal/log` に、hashで検索したアイテムのcontentを書き換え、`UpdatedAt`を更新する関数を追加する（状態による分岐は無く、contentの妥当性検証も行わない。空文字列であってもそのまま適用する）
  - 編集後も`Hash`/`CreatedAt`/`Closed`/`StartedAt`/`Tags`が変更されないことを検証するテストを書く
  - 未着手・着手中・完了いずれの状態のタスク、およびメモのいずれでも編集できることを検証するテストを書く
  - 空文字列のcontentでも拒否されずそのまま適用されることを検証するテストを書く
  - 存在しないhashを検索・編集しようとした場合にエラーになることを検証するテストを書く
  - Observable: `go test ./internal/log/...` で新規テストが全てパスし、編集後`UpdatedAt`以外のフィールドが編集前と一致することが確認できる
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 3.1, 3.2, 4.1, 4.2_
  - _Boundary: log.Edit_

- [x] 1.2 (P) エディタ起動によるcontent解決ロジックとユニットテスト
  - 新規パッケージに、現在のcontentを一時ファイルに書き込み、注入された起動処理でエディタを起動し、保存後の内容を読み戻す関数を実装する
  - 起動処理（実際のプロセス呼び出し）は引数として注入可能にし、テストでは偽の起動処理を使う（実プロセスは起動しない）
  - `$EDITOR`→`$VISUAL`→`vi`の優先順位でエディタ名を決定する関数を実装する
  - 保存後の内容が編集前と異なり、かつ空文字列でない場合にその内容が返ることを検証するテストを書く
  - 保存後の内容が編集前と完全に同一、または空文字列の場合に、内容を適用すべきでないと判定されることを検証するテストを書く
  - 起動処理がエラーを返した場合、そのエラーがそのまま返ることを検証するテストを書く
  - 一時ファイルが、起動処理の成否にかかわらず最終的に削除されることを検証するテストを書く
  - Observable: `go test ./internal/editor/...` で新規テストが全てパスし、偽の起動処理を使って「変更あり」「無変更」「空文字列」「起動エラー」の4パターンそれぞれが想定通りの結果を返すことが確認できる
  - _Requirements: 2.2, 2.3, 2.4, 2.5, 2.6, 2.7, 2.8_
  - _Boundary: internal/editor_

- [x] 2. command層への統合とテスト
  - `internal/command` に、当日ログのアイテムを読み取り専用で取得する関数を追加する（キャリーフォワードのような書き込み副作用を起こさないこと）
  - `internal/command` に、1.1で実装した編集ロジックを使って当日ログのcontentを書き換え、永続化し、編集確認を出力する関数を追加する
  - `internal/command` に、編集が中断されたことを通知する関数を追加する（`internal/view`に出力処理を追加し、そこへ委譲する）
  - `internal/view` に、編集確認（既存の確認出力パターンを再利用）と中断通知の出力処理を追加する
  - 当日ログに存在するアイテムに対して、直接指定された内容で正しく書き換えられることを検証する統合テストを書く
  - 当日ログに存在しないhash（過去日にのみ存在するhashを含む）を指定した場合にエラーになることを検証する統合テストを書く
  - メモ・未着手・着手中・完了タスクのいずれでも編集できることを検証する統合テストを書く
  - 読み取り専用の取得が当日ログファイルを新規作成しない（副作用が無い）ことを検証する統合テストを書く
  - Observable: `go test ./internal/command/...` で新規テストが全てパスし、編集後に`view`経由での確認出力（またはエラー）が正しく行われることが確認できる
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 2.1, 2.6, 2.7, 3.1, 3.2, 4.1, 4.2_
  - _Boundary: command.Edit, command.TodayItem, view.Edited_
  - _Depends: 1.1_（1.2のエディタ起動ロジックはこのタスクでは使用しないため、1.2の完了は前提としない）

- [x] 3. `edit` コマンドのCLI統合とエンドツーエンドテスト
  - `list`等と同じパターンで `edit` サブコマンドを登録する。hash引数は必須、content引数は省略可能にする
  - content引数が指定された場合は、2で実装したcontent書き換え処理を直接呼ぶ
  - content引数が省略された場合は、2で実装した読み取り専用取得で現在のcontentを取得し、1.2で実装したエディタ解決ロジックに渡す。結果に応じて書き換え処理または中断通知を呼ぶ。エディタ起動自体が失敗した場合はエラーとして終了する
  - 実際のエディタプロセスを起動する処理（注入用の実装）を実装する
  - 直接指定モードでcontentが書き換わることを検証するエンドツーエンドテストを書く
  - エディタモードを、一時的なスクリプトを`$EDITOR`に設定して検証するエンドツーエンドテストを書く（スクリプトが内容を書き換えるケースと、何もしない＝中断になるケースの両方）
  - Observable: `sava edit <hash> "new content"` と `sava edit <hash>`（エディタ経由）の両方が、実際のバイナリ経由で期待通りに動作する
  - _Requirements: 1.1, 2.1, 2.2, 2.5, 2.6, 2.7, 2.8_
  - _Boundary: cmd.newEditCommand_
  - _Depends: 1.2, 2_（エディタ解決ロジックとcommand層の両方が必要）
